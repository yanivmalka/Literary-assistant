# Dynamic place schema and containment relationships

This change replaces the fixed location form with project-defined place types and fields, and adds direct child-to-container relationships for extraction and manual editing. Values remain in `knowledge_entities.structured_fields`, while containment uses `knowledge_entity_relationships` and a branch-aware display helper. The extraction prompt accepts story-specific fields and converts explicit containment hints into `contained_in` edges. **Watch for:** **high, confirmed** backward-compatibility data loss when an existing legacy location is saved; **high, confirmed** custom labels that violate the new database key constraints; and **high, confirmed** branch edits that cannot remove inherited Main containment edges.

**Verdict**: NEEDS_CHANGES

## High-level view

The new UI selects catalog or project-defined place types and renders dynamic fields, but **high, confirmed** it reconstructs `structured_fields` from only the selected schema, so legacy geographic keys are lost on edit. **Medium, confirmed** required/select field metadata is not enforced by the form.

Containment direction is **confirmed** for newly created `contained_in` rows: child is the source and container is the target. **High, confirmed** branch removal does not consider inherited Main edges, and **medium, confirmed** the hub does not reload hierarchy data when an existing location’s edges change.

Extraction accepts `attributes.location_fields` and copies those values into structured fields. **High, confirmed** the normalization path stops copying old geographic fields despite still declaring them, and **low, likely** the custom-field prompt list is emitted with escaped rather than actual line breaks.

<summary>Issues (9)</summary>

1. **Legacy location fields discarded on edit** — **High, confirmed:** `LocationEditModal` rebuilds `structured_fields` from only `getPlaceFields(effectiveType, effectiveSchema)`, dropping legacy keys such as `continent`, `country`, `region`, and `city` when an existing location is saved. Merge the existing object or provide compatibility fields before writing.
2. **Legacy extraction fields discarded** — **High, confirmed:** both location structured-field builders no longer copy the declared `continent`, `country`, `region`, and `city` properties, so older extraction payloads lose those values. Preserve them as compatibility fields while migrating to relationships/dynamic fields.
3. **Non-ASCII custom keys violate database constraints** — **High, confirmed:** `toPlaceTypeKey` retains Unicode letters, while the migration permits only ASCII lowercase keys. Generate an ASCII-safe slug and handle collisions before inserting custom types or fields.
4. **Dynamic field metadata is cosmetic** — **Medium, confirmed:** required fields are marked but never validated, and `select`/`multi_select` definitions render as free-text inputs. Enforce required values and render/serialize each declared field type according to its schema.
5. **Fields added before creating a custom type are orphaned** — **Medium, confirmed:** a field added while the selector is `other` is stored under `place_type_key = 'other'`, then saving the location creates a different generated type key. Create the type first or rebind pending fields to the generated key.
6. **Branch removal does not tombstone inherited containment** — **High, confirmed:** branch save queries only branch `contained_in` additions, so unchecking a parent that exists in Main creates no `remove` row and the inherited edge remains effective. Compare against approved Main edges and write a branch tombstone with `base_exists: true`.
7. **Containment display stays stale after editing** — **Medium, confirmed:** `LocationsHub` reloads hierarchy only when `locations.length` changes. Saving containment for an existing location leaves `parentsByChild` and the tile unchanged until another dependency changes; explicitly reload the hierarchy after save.
8. **`parent_of` edges cannot be edited through the containment control** — **Medium, confirmed:** the loader treats `parent_of` as containment, but both save paths delete/query only `contained_in`. A loaded legacy `parent_of` remains after the user unchecks it and can coexist with the newly saved representation; handle both relationship types or migrate them.
9. **Custom-field extraction prompt formatting is malformed** — **Low, likely:** `.join("\\n")` emits backslash-n characters rather than line breaks, making the project-field list a single escaped line in the model prompt. Use a real newline and add a prompt-contract test.

### Legacy schema compatibility across the UI and extractor

**Confirmed:** the modal initializes from the existing structured object, but save creates a fresh object by iterating only the dynamic fields for the selected type (`client/src/components/knowledge/LocationEditModal.tsx:129-133`). An older location with `continent`/`country`/`region`/`city`, or any unknown story-specific key, therefore loses those values on an unrelated rename or description edit. **Confirmed:** the same compatibility gap exists in extraction: the `ExtractedEntity` interface still declares the legacy geographic properties (`supabase/functions/extract-knowledge/normalization.ts:41-44`), but the new location builders copy only the type, description, `location_fields`, optional `parent_location`, and narrative fields (`normalization.ts:148-162`; `extract-knowledge/index.ts:255-266`).

### Dynamic place type and field contract

**Confirmed:** `toPlaceTypeKey` permits Unicode letters and returns them unchanged (`client/src/lib/placeSchema.ts:146-149`), while `knowledge_place_types.type_key` and `knowledge_place_field_definitions.field_key` require ASCII lowercase keys (`supabase/migrations/134_dynamic_place_schema.sql:9,22-24`). Hebrew or other non-Latin labels therefore fail at insertion. **Confirmed:** the form displays `is_required` only as an asterisk and falls back to a text input for `select` and `multi_select` (`LocationEditModal.tsx:231-241`), so persisted values do not reliably follow the declared schema.

**Confirmed:** a custom field can be created while `selectedPlaceType` is `other`, but the save path subsequently creates a generated custom type and switches to that key (`LocationEditModal.tsx:118-126,186-195`). The field remains attached to `other`, so it is absent from the new type’s field list and future extraction instructions.

### Child-to-container graph and branch behavior

**Confirmed:** the extraction path emits child as `character_a`, container as `character_b`, and `contained_in` before resolving both names to IDs (`supabase/functions/extract-knowledge/index.ts:1860-1907`). **Confirmed:** the hierarchy loader translates `parent_of` into child-to-parent display (`client/src/lib/placeHierarchy.ts:36-53`), but branch save inspects only branch additions (`placeHierarchy.ts:67-78`), so a Main edge is never removed when unchecked. **Confirmed:** it also treats `parent_of` as containment display while never removing that type in either Main or branch mode (`placeHierarchy.ts:67-113`).

**Confirmed:** the tile receives resolved parent names and formats them under “נמצא בתוך” (`client/src/components/knowledge/LocationsHub.tsx:72`; `client/src/components/knowledge/LocationTile.tsx:20-32`). The hub effect depends on `locations.length`, not a save/reload signal (`LocationsHub.tsx:35-42`), so an edge edit on an existing location does not refresh the displayed relationship.

### Prompt, normalization, and persistence contract

**Confirmed:** the prompt asks for `attributes.location_fields`, and both builders read that nested object and copy its entries into `structured_fields` (`supabase/functions/_shared/rules/prompt.ts:185-191`; `extract-knowledge/index.ts:255-264`; `normalization.ts:148-157`). **Likely:** the project-field extension is formatted with `.join("\\n")` (`extract-knowledge/index.ts:197-204`), which should be corrected and covered by a prompt snapshot test.
